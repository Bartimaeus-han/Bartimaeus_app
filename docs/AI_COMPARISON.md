# Claude vs 타 AI 비교 로그 (AI Comparison Log)

이 문서는 트러블슈팅 과정에서 Claude가 스스로 근본 원인을 찾지 못하고, 사용자가 Gemini 등 타 AI 모델에게 별도로 문의하여 얻은 답이 실제 해결의 결정적 단서였던 사례를 기록합니다.

목적은 단순히 "누가 더 잘했다"는 승패 기록이 아니라, **Claude가 어떤 접근/가설 순서를 취했길래 놓쳤는지**와 **타 AI의 답변이 어떤 관점의 차이로 적중했는지**를 분석해서, 향후 유사 상황에서 Claude가 더 빨리 그 관점을 채택하도록 하는 데 있습니다.

**이 문서는 죽은 기록이 아니라 살아있는 체크리스트입니다.** 아래 상단의 "누적된 핵심 교훈"은 Claude가 트러블슈팅 도중 가설이 연달아 기각되어 막히는 상황(스스로 헛다리를 짚고 있다고 의심되는 시점)에 실제로 다시 펼쳐보고 점검해야 하는 목록입니다. 새 사례가 추가될 때마다 그 사례의 핵심을 한두 문장으로 압축해 이 체크리스트에도 반드시 함께 추가합니다.

## 🔑 누적된 핵심 교훈 (체크리스트)

- **[리소스 제한 디버깅]** 프로세스가 알 수 없는 이유로 응답 없음/hang 상태에 빠졌는데 외부 네트워크 경로(포트, 방화벽, NAT, 드라이버 등)를 다 뒤져도 안 나오면, 네트워크 계층을 더 파기 전에 **프로세스 자체의 리소스 사용량부터 실측**(`/proc/[pid]/status`, `docker stats`, cgroup 파일)하고, 관련 리소스 제한 API(`RLIMIT_AS`, `ulimit`, cgroups 등)가 정확히 어떤 지표(RSS vs VSS 등)를 근거로 동작하는지 개념부터 재확인할 것. ## 사례 1. `localhost:9090` 접속 불량 — RLIMIT_AS(VSS) 소진 (2026-07-31)

### 증상
Docker 컨테이너(`bartimaeus-app`)가 정상 `Up` 상태였고 TCP 3-way handshake까지는 성공했지만, 실제 HTTPS 요청(`curl`)은 매번 응답 없이 타임아웃됨.

### Claude가 스스로 시도했던 접근 (1~3차 세션, 실패)
네트워크/인프라 계층 위주로 가설을 세우고 하나씩 소거하는 방식으로 접근했음:
1. curl의 IPv6(`::1`) 우선 시도 문제 → IPv4 강제해도 동일
2. **자기 자신이 유발한 Slowloris형 스레드 고갈**: 디버깅 중 반복한 미완성 TLS 연결들이 cpp-httplib 워커 스레드 풀을 영구 점유 — 실제 존재하는 취약점이었지만 이번 증상의 원인은 아니었음
3. `wslrelay.exe` vs `com.docker.backend.exe` 포트 릴레이 충돌 → `wsl --shutdown` 시도 → 미해결
4. Windows 포트 제외 범위(`netsh excludedportrange`) → 혐의 없음
5. Realtek NIC의 LSO(Large Send Offload)가 Hyper-V 가상 스위치에서 패킷을 블랙홀시키는 문제 → `Disable-NetAdapterLso` 제안 → 미해결
6. 컨테이너 내부에서 자기 자신에게 접속해도 동일하게 멈추는 것 확인 → Windows/Docker 네트워킹은 배제, 앱 레벨 문제로 방향 전환
7. 별도로 DB 커넥션 풀 고갈 버그(THREAT-07, MariaDB 재시작 시 재연결 실패)도 발견해 수정함 — 실제 버그였고 고쳐야 했던 것은 맞지만, 이번 접속 불량의 원인은 아니었음

즉, "네트워크 경로의 어딘가가 막혀 있다"는 프레임에 갇혀서 계속 그 층위 안에서만 가설을 세웠고, 정작 **자신이 코드에 넣어둔 `setrlimit(RLIMIT_AS, 128MB)` 자체의 성격**은 의심하지 않음.

### Gemini가 제시한 관점 (사용자가 별도로 문의)
`RLIMIT_AS`는 **RSS(물리 메모리 실사용량)가 아니라 VSS(가상 주소 공간 예약량)를 제한하는 API**라는 점을 짚어줌. 64비트 Linux 멀티스레드 프로그램은 스레드마다 기본 8MB 스택을 미리 예약하기 때문에, 실제 공격이나 부하 없이도 스레드 수만으로 VSS 한도가 소진될 수 있다는 지적.

### 검증 및 근본 원인 확정 (Claude가 실측으로 재확인)
`docker exec bartimaeus-app cat /proc/1/status`로 직접 확인:
```
VmPeak:   127036 kB   (~124 MB)
VmSize:   127036 kB   (~124 MB)  ← RLIMIT_AS 128MB 한도 대비 97% 소진
VmRSS:      9652 kB   (~9.4 MB) ← 실제 물리 메모리 사용량은 이것뿐
Threads:  15
```
스레드 15개 × 기본 스택 8MB만으로 이미 ~120MB — Idle 상태에서부터 방어선이 거의 다 차 있었던 것. 새 연결이 들어와 신규 스레드가 스택을 할당하려는 순간 VSS 한도에 걸려 조용히 실패 → TCP accept는 되지만 TLS 핸드셰이크를 처리할 스레드가 못 떠서 클라이언트 입장에서는 에러 없이 무한 대기(hang)로 관측됨.

### 최종 해결
[main.cpp](../src/main.cpp)의 `limitProcessMemory(128)` → `limitProcessMemory(512)`로 상향 (사용자가 직접 수정·재빌드). 임시방편이며, 근본적으로는 스레드 스택 크기 축소(`pthread_attr_setstacksize`)나 cgroups 기반 물리 메모리 제한 전환이 필요함 (TODO.md에 후속 과제로 등록됨).

### Claude가 놓친 이유에 대한 분석
- 문제를 처음부터 "외부(네트워크/OS/Docker) 계층"으로 프레이밍하고, 그 프레임 안에서만 가설을 순차 소거함. 자신이 직접 작성/제안했던 방어 코드(`RLIMIT_AS` 설정)를 의심 대상에서 배제하는 사각지대가 있었음.
- `RLIMIT_AS`라는 API 이름과 "메모리 제한"이라는 표면적 의미만 보고, **VSS와 RSS의 개념적 차이**(무엇을 세는 지표인가)까지 파고들지 않음 — 로그에 이미 찍히고 있던 "Physical Memory (resident): 8.75MB"라는 수치를 보고도 "여유 있다"고 오판하며 그 지표(RSS)와 실제 제한 대상(VSS)이 다르다는 걸 연결짓지 못함.
- Gemini의 힌트를 받은 뒤에는 `/proc/1/status` 실측으로 즉시 검증·확정까지 갔음 — 즉 **실측 능력이나 도구 사용 자체의 문제가 아니라, "어느 방향을 파봐야 하는가"에 대한 최초 가설 설정 단계에서의 차이**였음.

### 향후 적용 지침
시스템 리소스 제한(RLIMIT, ulimit, cgroups 등)을 다루는 코드가 관련된 장애를 디버깅할 때는, 외부 네트워크 계층을 다 뒤지기 전에 **먼저 프로세스 자체의 리소스 사용량을 실측**(`/proc/[pid]/status`, `docker stats`, cgroup 파일 등)하고, 그 리소스 제한 API가 정확히 어떤 지표(RSS vs VSS 등)를 근거로 동작하는지부터 개념적으로 재확인하는 단계를 가설 목록의 앞쪽에 둘 것.
